# dllmgr — менеджер вариантов DLL для Wine (+ скилл wine-fix). Концепция v0.2

Рабочее название `dllmgr`; итоговое имя выбирает владелец. Часть проекта Marwin:
код — в `dllmgr/`, скилл — в `skills/wine-fix/` этого репозитория.
Язык — Go, GUI — `github.com/unxed/goWidgets`.

## 0. Зачем

Системный Wine из репозитория дистрибутива (Mint 22 → Wine 9.0). Нужно уметь:
«возьми comctl32 из Wine 11 и включи её **только для FastStone** (`FSViewer.exe`,
любая версия, установленный или portable) в префиксе `~/.wine`; откат одной кнопкой».
И так же публиковать собственные реализации DLL (например, cc580 — comctl32 5.80 на bp)
в общий каталог, чтобы другие ставили их тем же способом.

Не цели: менять системный Wine; DLL от Microsoft (это winetricks); замена DLL с unix-частью
и ядра системы — их правят заплатки (§16).

Чем отличается от существующего: winetricks ставит нативные DLL Microsoft, в основном
на весь префикс; менеджеры префиксов дают выбрать версию лишь для фиксированного набора
компонентов (DXVK, VKD3D…), тоже на весь префикс.
Здесь — открытый каталог любых DLL, правило на конкретный exe и проверка, что правило
действительно сработало.

## 1. Термины

- **Вариант** — конкретная сборка DLL: `dll@provider:version/arch`, например
  `comctl32@wine:11.0/i386`, `comctl32@cc580:0.1/i386`.
- **Слот** — откуда модуль грузится в префиксе: `system` (system32 или syswow64 в
  зависимости от разрядности) или `sxs:<assembly>` (каталог в `winsxs`).
- **Правило** — (префикс, имя exe, dll, слот) → вариант.
- **Индекс** — git-репозиторий с TOML-манифестами; индексов может быть несколько.
- **Хранилище** — локальный кеш проверенных DLL, адресуемых по sha256.

## 2. Проверенные факты о Wine (опираться на них, не перепроверять)

Проверено по исходникам тегов `wine-9.0` и `wine-11.0`.

- **Ф1. Метка builtin.** У встроенных DLL Wine сразу за `IMAGE_DOS_HEADER` (смещение 0x40)
  лежат 32 байта `"Wine builtin DLL"`. Как загрузчик поступает с таким файлом
  (`dlls/ntdll/unix/loader.c`, `load_builtin()`): при порядке `native` — «не найдено»,
  при любом другом — грузит **свою** встроенную DLL из каталога установки. Поэтому
  DLL из другой версии Wine без доработки игнорируется. Решение: обнулить эти
  32 байта (назовём это «снять метку»). Файлы с меткой `"Wine placeholder DLL"` — пустые
  заглушки без кода, их не принимаем.
- **Ф2. Порядок загрузки** (`dlls/ntdll/unix/loadorder.c`: `get_load_order`,
  `get_load_order_value`). Для каждой формы имени по очереди проверяются
  `WINEDLLOVERRIDES`, затем `HKCU\Software\Wine\AppDefaults\<exe>\DllOverrides`, затем
  `HKCU\Software\Wine\DllOverrides`. Формы имени: полный путь без расширения (для файлов
  из системного каталога — просто имя), потом `*имя`, потом `имя`. Если переопределения
  нет (`LO_DEFAULT`), побеждает встроенная DLL, даже когда найден нативный файл; исключение —
  встроенная с флагом PREFER_NATIVE. Отсюда два следствия: без явного переопределения наш
  файл не загрузится, а другие программы его не подхватят.
- **Ф3.** При порядке `native,builtin` файл без метки грузится как native, а нетронутый
  файл с меткой по-прежнему даёт встроенную DLL Wine (`load_builtin` превращает порядок в
  `LO_BUILTIN_NATIVE`). Поэтому всегда пишем `native,builtin`, а не `native`.
- **Ф4.** wineboot при обновлении Wine (`dlls/setupapi/fakedll.c`: `create_dest_file`,
  `is_fake_dll`) не перезаписывает файлы без метки builtin или placeholder. Значит, наш
  файл переживает обновление Wine — и продолжает использоваться. Нужно отслеживать смену
  версии Wine.
- **Ф5.** В Wine 9 одна comctl32 обслуживает и v5, и v6 (v6 — через winsxs). В Wine 11 это два
  модуля: `comctl32.dll` и `comctl32_v6.dll` (`dlls/comctl32_v6`, ставится в system32).
  Импорты тоже изменились: в 11 добавились `oleaut32` и отложенный `oleacc`. Значит,
  «comctl32 из Wine 11» — это два варианта, и для Wine 9 v6-вариант кладётся в слот winsxs
  под именем `comctl32.dll`. Что именно нужно FastStone, покажет спайк И0.
- **Ф6. Строки логов** (`dlls/ntdll/loader.c`): `trace:loaddll … Loaded <путь> at <адрес>: native|builtin`;
  отсутствующий импорт — WARN в канале `module`:
  `No implementation for X.Y imported from Z, setting to …`. Нужен
  `WINEDEBUG=+loaddll,warn+module`. Отсутствующий импорт не мешает загрузке, падение
  будет при вызове.
- **Ф7.** В пуле WineHQ `https://dl.winehq.org/wine-builds/ubuntu/pool/main/w/wine/`
  есть i386-пакеты Wine 11 под noble: `wine-stable-i386_11.0.0.0~noble-1_i386.deb`,
  `wine-devel-i386_11.21~noble-1_i386.deb` (состояние на 2026-11-06). Путь внутри пакета
  ищем find'ом по `*/i386-windows/<dll>.dll`, не захардкоживая префикс.

Гипотезы, которые проверяет спайк И0:
- **Г1.** comctl32 из Wine 11 со снятой меткой грузится в Wine 9 как native; если есть
  «No implementation», видно, каких функций не хватает.
- **Г2.** FastStone грузит comctl32 из system (v5) или из winsxs (v6) — какой из них.
- **Г3.** Нужные баги FastStone в Wine 11 действительно исправлены. В том диалоге 59609
  воспроизводился и на 11.12, так что исправлено не всё.
- **Г4.** `comctl32_v6.dll`, положенный в winsxs под именем `comctl32.dll`, работает.

## 3. Модель: декларативное состояние + идемпотентная синхронизация

Префикс описывается набором правил (желаемое состояние) и запомненными оригиналами.
Любое действие — изменить набор правил и вызвать `reconcile()`.
- Откат = убрать правило. `reset` = убрать все правила, и префикс побайтно возвращается к исходному.
- Защита от сбоев бесплатна: reconcile идемпотентен, повторный запуск доводит прерванную операцию до конца.
- «Отменить последнее» берёт снимок «до» из `history.jsonl` (снимки набора правил до и после каждой правки).

`$WINEPREFIX/dllmgr/state.json` (вне `drive_c`, переезжает вместе с префиксом):
```json
{
  "schema": 1,
  "rules": [{
    "app": "FSViewer.exe", "dll": "comctl32", "slot": "system",
    "variant": "comctl32@wine:11.0/i386", "sha256": "…",
    "wine_at_apply": "wine-9.0 (Ubuntu …)", "exe_paths": ["…"], "added": "…"
  }],
  "originals": {
    "files": {"drive_c/windows/syswow64/comctl32.dll":
              {"sha256": "…", "backup": "dllmgr/backup/<sha256>", "symlink_to": null}},
    "reg":   {"HKCU\\Software\\Wine\\AppDefaults\\FSViewer.exe\\DllOverrides\\comctl32":
              {"absent": true}}
  }
}
```

Алгоритм `reconcile()`:
1. Из правил строим желаемые файлы `слот → sha256`. Если на один путь претендуют два
   разных хеша — ошибка ещё до любых изменений (конфликт, назвать оба правила).
2. Желаемые значения реестра: на каждое правило `AppDefaults\<exe>\DllOverrides\<dll>=native,builtin`.
   Плюс глобальное `<dll>=builtin`, если у встроенной DLL целевого Wine стоит PREFER_NATIVE
   (иначе наш файл подхватят все программы).
3. Для каждого пути из объединения «желаемое ∪ оригиналы»:
   - если файл желаем: текущий == желаемый → ничего; текущий == оригинал (или оригинал ещё
     не записан) → сохранить оригинал (один раз) и записать наш; иначе **расхождение**;
   - если правило убрали: текущий == наш → вернуть оригинал и забыть о нём; текущий == оригинал → забыть;
     иначе **расхождение**.
   - Расхождение: остановиться и показать, что изменилось и кем, например winetricks cc580.
     Принять текущее состояние за новый оригинал — только по явному `--adopt`.
4. Те же правила для значений реестра (через интерфейс `Registry`).
5. Запись — только через временный файл в том же каталоге + rename. Через симлинк не
   писать никогда: если слот — симлинк (скажем, в системный каталог Wine), заменяется сама
   ссылка, а её цель запоминается в оригинале.
6. `state.json` сохраняется атомарно после каждой успешной операции.

## 4. Проверки перед применением (все до первого изменения, fail fast)

- a. **Разрядность.** Архитектура префикса — строка `#arch=win32|win64` в `system.reg`. Разрядность
  варианта должна подходить префиксу; если известен путь к exe — ещё и совпадать с `Machine` в его PE.
  i386 в win64 → `syswow64`, i386 в win32 → `system32`, x86_64 → `system32`; x86_64 в win32 — ошибка.
- b. **Заменяемость.** DLL не в запретном списке (`ntdll kernel32 kernelbase win32u user32 gdi32 wow64*`,
  `*.drv`) и не имеет unix-части: в каталоге целевого Wine нет `<arch>-unix/<dll>.so`, а для
  вариантов от провайдера wine — и в исходном архиве. Незаменяемые DLL не меняются, а
  правятся заплатками (§16).
- c. **Файл варианта.** Корректный PE, флаг DLL, не placeholder, метка снята.
- d. **Импорты** (п. 5). Обычные импорты — ошибка, отложенные — предупреждение; строгость задаётся в конфиге.
- e. **Слот найден.** Для `sxs:` glob по `winsxs/<x86|amd64>_<assembly>_*` должен дать ровно один
  каталог, иначе ошибка со списком кандидатов.
- f. **Конфликты** (п. 3.1).
- g. **Предупреждения.** `WINEDLLOVERRIDES` упоминает эту dll (переменная перекроет правило);
  глобальное переопределение dll с native первым; ключ `*dll` (перекроет правило для sxs-пути).

## 5. Статическая проверка импортов (`check`)

`debug/pe` из стандартной библиотеки знает только импорты по имени. Нужен свой минимальный разбор
(~300 строк): импорты по ординалу, каталог отложенных импортов, каталог экспорта (имена,
ординалы, форвардеры).

Как разрешается каждая импортируемая DLL: (1) другой вариант из правил того же exe;
(2) встроенная DLL целевого Wine `<dll_dir>/<arch>-windows/<dll>.dll`; (3) иначе — ошибка.
Форвардеры — на одну ступень. `api-ms-win-*` — обычные файлы в каталоге встроенных DLL.
Результат: «ok» или список вида `user32.Foo (импорт)`, `oleacc.Bar (delay)`. Чего проверка
не видит: экспорт-заглушку Wine и разницу в поведении. Это ловит `verify`.

Поиск целевого Wine: `wine --version`. Кандидаты на каталог встроенных DLL:
`/usr/lib/<triplet>/wine/<arch>-windows`, `/usr/lib/wine/<arch>-windows`,
`/opt/wine-*/lib/wine/<arch>-windows`, `<realpath(wine)>/../lib/wine/<arch>-windows`,
плюс переопределение в конфиге `wine.dll_dirs`. Каталог годится, если в нём есть `ntdll.dll`
с меткой builtin. Ничего не нашлось — ошибка с просьбой указать путь в конфиге. Не угадывать.

## 6. Живая проверка (`verify`)

`WINEPREFIX=… WINEDEBUG=+loaddll,warn+module wine <exe>`, stderr пишется в
`$WINEPREFIX/dllmgr/logs/<ts>.log`. Компактный отчёт, не больше 15 строк: по каждой управляемой dll —
откуда загружена, native или builtin, совпало ли с ожиданием, sha256 физического файла.
Плюс «No implementation …» без повторов, не больше 10. Для 32-битной программы в win64-префиксе
путь `C:\windows\system32\…` в логе физически означает `syswow64`; сверить по эталонным логам из И0.
Ждём выхода программы; `verify.timeout_sec` (0 — до выхода). Парсер тестируется на эталонных
логах с машины пользователя.

## 7. Индекс

Отдельный репозиторий. Раскладка `dlls/<dll>/<provider>-<version>-<arch>.toml`.
Скачивается архивом по HTTPS, git не нужен. В конфиге `taps = [{name, url}]`; при добавлении
неофициального индекса — явное предупреждение.

```toml
schema   = 1
dll      = "comctl32"
file     = "comctl32.dll"               # имя файла в слоте
provider = "wine"
version  = "11.0"
arch     = "i386"
slot     = "system"                     # или "sxs:microsoft.windows.common-controls"
license  = "LGPL-2.1-or-later"
source   = "https://gitlab.winehq.org/wine/wine/-/tree/wine-11.0/dlls/comctl32"
summary  = "comctl32 (v5) из Wine 11.0"
fixes    = []                           # "winehq:NNNNN"
[fetch]
urls   = ["https://dl.winehq.org/wine-builds/ubuntu/pool/main/w/wine/wine-stable-i386_11.0.0.0~noble-1_i386.deb"]
sha256 = "…"                            # архива
format = "deb"                          # deb | tar.xz | tar.zst | raw
member = "*/i386-windows/comctl32.dll"  # glob, ровно одно совпадение
member_sha256 = "…"                     # извлечённого файла до снятия метки; по нему проверяется результат
```

- DLL Wine индекс **не перезаливает**: манифест указывает на официальную сборку апстрима,
  файл извлекается из неё.
  Лицензия и доверие остаются за апстримом.
- Сторонние провайдеры (cc580): `format = "raw"` — ассет релиза; `source` и открытая `license`
  обязательны, без них CI индекса манифест не принимает. DLL Microsoft не принимаются.
- Спецификация варианта: `dll@provider:version[/arch]`; `latest` — максимальная версия
  (сравнение по числовым компонентам). В правило записывается уже конкретная версия.
- .deb разбирается так: ar (свой разбор, ~50 строк) + `data.tar.{xz,zst}` через
  `github.com/ulikunitz/xz` и `github.com/klauspost/compress/zstd` (чистый Go).

Публикация:
- `dllmgr add-local <file.dll> --provider P --version V` — локальный вариант без индекса
  (для авторов DLL и для скилла).
- `dllmgr pack <file.dll> --provider … --version … --url … --source … --license …` — выдаёт
  TOML-манифест с хешами, разрядностью и результатом проверки импортов против локального Wine.
- Позже: `pack-wine <archive> --version X` — манифесты на все заменяемые DLL релиза Wine;
  CI индекса — проверка схемы, хешей и матрица совместимости импортов по нескольким версиям Wine.

## 8. Локальные пути и конфиг

`~/.config/dllmgr/config.toml`; `~/.cache/dllmgr/dl/<sha256>` (архивы, можно удалять);
`~/.local/share/dllmgr/store/<sha256>.dll` (метка снята); `~/.local/share/dllmgr/index/<tap>/`;
`$WINEPREFIX/dllmgr/{state.json,history.jsonl,backup/,logs/}`.

Конфиг: `wine.binary="wine"`, `wine.dll_dirs=[]`, `prefixes=[]`, `taps=[…]`,
`strict_imports=true`, `verify.debug="+loaddll,warn+module"`, `verify.timeout_sec=0`,
`keep_archives=true`.

## 9. CLI

```
dllmgr index update
dllmgr search <dll>            dllmgr info <variant>
dllmgr check <variant> [--app <exe-path>]
dllmgr apply --app <exe|path> <variant> [--slot …] [--prefix …] [--yes]
dllmgr remove --app <exe> <dll>      dllmgr reset      dllmgr undo
dllmgr status                        # правила, расхождения, «Wine сменился с момента применения»,
                                     # «встроенная уже не старее варианта — правило можно убрать»
dllmgr verify --app <exe-path>
dllmgr add-local …   dllmgr pack …
dllmgr gui
```
Префикс по умолчанию — `$WINEPREFIX`, иначе `~/.wine`. Перед изменениями печатается план;
`--yes` пропускает подтверждение.

## 10. GUI на goWidgets

goWidgets: нативные контролы, без CGO. Есть Window, Label, Button, CheckBox, Edit, ComboBox,
ListBox, Table, TextView, ImageView, Canvas, Message/Confirm/Ask, файловые диалоги, трей;
есть headless-бэкенд. Перед работой прочитать README, `docs/disdoc.md`, `docs/adr/`, `AGENTS.md`.
Если нужного виджета нет — остановиться и спросить; виджеты внутри dllmgr не писать.

Одно окно:
- ComboBox «Префикс».
- Table правил: «Программа | DLL | Вариант | Состояние».
- Кнопки «Добавить…», «Убрать», «Сменить вариант», «Проверить запуском», «Обновить индекс».
- TextView с логом.

Сценарий «Добавить»:
1. Файловый диалог → exe.
2. Надпись «Правило для всех FSViewer.exe в префиксе ~/.wine».
3. ComboBox DLL (отфильтрован по разрядности exe).
4. ComboBox варианта: свежие сверху, с отметкой результата `check`.
5. «Применить» → Confirm с текстом плана → reconcile → предложить «Проверить запуском».

GUI — тонкий слой над теми же пакетами, что и CLI; логики в UI нет.

## 11. Структура кода

```
cmd/dllmgr/        CLI + подкоманда gui
internal/pe/       разбор PE: machine, импорт (имя/ординал/delay), экспорт+форвардеры,
                   метки builtin/placeholder, PREFER_NATIVE, Unmark()
internal/wine/     поиск wine, версия, каталоги dll, unix-часть, запуск с WINEDEBUG
internal/prefix/   арх префикса, разрешение слотов
internal/reg/      интерфейс Registry; реализация через `wine reg add/query/delete`; fake
internal/index/    манифесты, индексы, разбор спецификации варианта, latest
internal/fetch/    загрузка с кешем, sha256, deb/tar.xz/tar.zst/raw
internal/store/    хранилище по sha256
internal/compat/   проверка импортов
internal/state/    state.json, history.jsonl, reconcile()
internal/verify/   парсер +loaddll / warn+module
ui/                goWidgets
```
TOML — `github.com/BurntSushi/toml`; остальное — стандартная библиотека.

## 12. Тесты

- `testdata/`: крошечные PE (DLL/EXE i386 и x86_64), собранные mingw, лежат в репозитории
  вместе с `testdata/gen.sh`. Копии с меткой builtin создаются в самих тестах.
- pe: импорты по имени, по ординалу и отложенные; экспорт, форвардеры; `Unmark` идемпотентен
  и меняет ровно 32 байта; placeholder отвергается.
- compat: A импортирует `B.f1, B.f2, B.#7`, B экспортирует только `f1` → отчёт `f2, #7`.
- state: фейковый префикс в `t.TempDir()` (`system.reg` с `#arch=win64`, `syswow64/comctl32.dll`
  с меткой) + фейковый Registry.
  - add → файлы и реестр; remove → побайтно как было.
  - Расхождение → ошибка без изменений.
  - Конфликт.
  - Цель симлинка не тронута.
  - Сбой после первой операции → повторный reconcile доводит до конца.
- fetch: .deb собирается в памяти (ar + tar.xz / tar.zst) → извлечение. Несовпадение хеша,
  0 или 2 совпадения glob → ошибка.
- verify: эталонные логи из И0 (даёт пользователь).
- Настоящий Registry — интеграционный тест, только если `wine` есть в PATH.
- GUI — смоук на headless-бэкенде, если тот позволяет.
- Сборку и тесты в песочнице запускать только с разрешения пользователя; сначала — патч.

- **И0 — спайк руками, без кода** (скрипт ниже). Проверяет Г1–Г4 и даёт эталонные логи.

  префиксе — сначала проверить порядок поиска и KnownDLLs в Wine), Windows как цель для cc580,

## 14. Открытые вопросы и риски

- Имя менеджера и репозиторий индекса (код менеджера — в `dllmgr/` этого репозитория).
- Если Wine 11 comctl32 требует экспортов, которых нет в Wine 9, этот вариант честно помечается
  «несовместим с Wine 9». Здесь выигрывает cc580, написанная на публичном API.
- Связи сверх импортов (uxtheme, общие классы окон v5/v6) — ловит `verify` и отчёты пользователей.
- Дистрибутив обновил Wine → `status` показывает, что правило могло устареть.
- Безопасность: DLL — это код. Хеши sha256 закреплены, исходники обязательны, сторонние индексы — только по явному согласию.

## 15. Смежное: скилл `wine-fix` (тот же репозиторий, `skills/wine-fix/`)

**Реалистичность.** «Любое приложение» — нет. Реалистичный класс задач: регрессии, ошибки
в «листовых» DLL и часть глубоких ошибок через заплатки; для остального — качественный отчёт.
Дёшево это становится за счёт dllmgr, который даёт три примитива:
1. Бисект по одной DLL между релизами Wine без установки Wine.
2. Сборка одной DLL из исходников точной версии.
3. Применение, откат и проверка для одной программы.

Целевой сценарий. У пользователя в FastStone в верхней панели видны не все превью
(bugs.winehq.org 59251). Он описывает проблему своему агенту и даёт ему ссылку на скилл.
Багтрекер Wine пользователь сам не смотрит. Агент:
1. определяет, в какой DLL проблема;
2. ищет подходящий тикет;
3. собирает эту DLL на системе пользователя;
4. исправляет её сам или применяет исправление из тикета;
5. прописывает исправленную DLL в Wine пользователя;
6. предлагает отправить отчёт: новый баг или комментарий в существующий тикет, с описанием,
   как это исправить, по опыту этого запуска.

От пользователя нужно только войти в багзиллу Wine, подтвердить глазами результат и разрешить отправку.

Конвейер:
1. **Воспроизвести и сузить.** Симптом описывает пользователь; визуальное подтверждает он же
   (скилл спрашивает, а не гадает). Данные собирает
   `dllmgr diag` (§17): скилл читает выжимку и просит полные логи только когда нужно.
2. **Найти модуль.** Бисект по релизам через dllmgr: подставить DLL из более нового или
   старого Wine. Где поведение меняется — там регрессия или исправление с точностью до
   релиза. Дальше git bisect по коммитам, затронувшим `dlls/<dll>`, локальными сборками:
   пересобирается одна DLL, это минуты.
   Параллельно — поиск тикета. REST API багзиллы Wine отвечает без входа (проверено 2026-11-06:
   `https://bugs.winehq.org/rest/bug?quicksearch=FastStone&include_fields=id,summary,status`
   нашёл 5129, 43490, 59251, 59609). Из найденных тикетов берутся симптомы, трассы и готовые
   патчи: вложения или ссылки на merge request в GitLab Wine.
3. **Минимальный репро.** Крошечная программа на C (mingw) воспроизводит ошибку без самого
   приложения: создать контрол, послать сообщение, напечатать результат. Запускается под
   Xvfb, код возврата — вердикт. Это одновременно доказательство ошибки, тест исправления
   и прозаическое описание будущего теста для Wine.
4. **Исправить.** Способы — в порядке выбора:
   1. Готовое исправление из тикета: `git apply` на исходники версии пользователя → сборка
      одной DLL → `add-local` + `apply` → `verify`.
   2. Своя правка исходников Wine на C той версии, что стоит у пользователя (или master, если
      `check` проходит), тем же путём. Такую правку проще всего принять в апстрим.
   3. Ошибка глубже (unix-часть, user32/win32u) — **заплатка** по §16: перехват сломанной
      функции с исправленным поведением; ставится через dllmgr тем же правилом.
   4. Переписать модуль с нуля — на Bp (как cc580): он быстрее собирается, и о памяти в нём
      думать меньше. Только когда модуль Wine по устройству не подходит программе или нужно
      другое эталонное поведение. Код на Bp в Wine не возьмут, отчёт остаётся текстовым.

   Не чиним (wineserver, графика и драйверы, тайминги, DRM и античиты) — только отчёт.
5. **Отчёт апстриму** — текст в bugs.winehq.org: новый баг или комментарий в найденный тикет.
   Агент готовит текст и отправляет только после «да» пользователя. Вход: пользователь
   логинится в багзиллу в браузере агента или один раз создаёт API-ключ в настройках
   профиля (тогда агент пишет через REST, без управления браузером). Шаблон:
   - программа и её версия, версии Wine, коммит регрессии;
   - симптом;
   - минимальный репро;
   - причина: файл, функция, строка на коммите X; как есть и как должно быть, со ссылками
     на документацию Microsoft;
   - исправление по шагам, с граничными случаями;
   - тест для `dlls/<dll>/tests` словами: подготовка, действия, ожидаемые значения;
   - как проверено.
   Критерий готовности: **отчёт проверяется делом**. Дешёвая модель-субагент получает только
   текст отчёта и дерево Wine, пишет по нему патч, патч собирается, репро проходит. Не прошло —
   отчёт недостаточно точен.
6. **Без кода Microsoft.** Никакого дизассемблирования DLL Microsoft и никаких утёкших исходников.
   Источники — документация Microsoft, тесты Wine и наблюдаемое поведение (это требование
   Wine к участникам).
7. **Самосовершенствование.** Если по своему опыту агент видит, как сделать скилл лучше,
   он сразу отправляет PR в unxed/Marwin: правку скилла, пресетов `diag` или инструментов.
   Примеры: шаг пришлось изобретать; не хватило пресета; инструкция оказалась неверной;
   встретился новый тип проблемы. В PR — что было, что изменить и на каком случае это
   выяснилось. Только обобщённый опыт: без данных, путей и логов с машины пользователя.
   Если отправить PR нельзя (нет доступа к GitHub), агент сохраняет предложение в файл и
   говорит об этом пользователю.

Где работает: локальный агент на машине пользователя (нужны приложение, Wine и дисплей).
Облачная песочница — только для сборки и статического анализа. Зависимости из репозитория
дистрибутива: mingw-w64 и пакеты для минимального configure Wine; место — на одно дерево
сборки Wine. Исходники точной версии пользователя берутся через `apt source wine`, так что
патчи Debian тоже на месте (нужны deb-src).

### Сборка одной DLL без сборки всего Wine

Проверено по `tools/makedep.c` тега `wine-9.0`. makedep генерирует один общий Makefile:
у каждого модуля своя цель `dlls/<dll>/all`, у инструментов сборки (winebuild, widl, wrc) —
цель `__tooldeps__`. `make` по ним собирает только замыкание зависимостей модуля:
- инструменты;
- заголовки, которые генерируются из IDL;
- библиотеки импорта зависимостей — из их `.spec` через `winebuild --implib`;
- сам модуль.

Рецепт (точные флаги уточняются на проверке блокеров):
```
./configure --enable-archs=i386,x86_64 --without-x --without-freetype   # + прочие --without-*
make __tooldeps__ dlls/comctl32/all
```
`--enable-archs` собирает PE-модули mingw. 32-битные системные библиотеки не нужны, а
результат — обычный PE, пригодный и для классического Wine 9.

**Если система сборки Wine так не умеет, учимся сами:** пишем свой минимальный сборщик одной DLL.
Он берёт `Makefile.in` модуля (`MODULE`, `IMPORTS`, `DELAYIMPORTS`, `EXTRADEFS`, `PARENTSRC`,
`SOURCES`) и `.spec` импортируемых DLL. Инструменты — Wine из того же дерева: winebuild,
widl и wrc собираются хост-компилятором отдельно.

**На старте — только проверка на принципиальные блокеры.** Скорость и место на диске
блокерами не считаются и на старте не оптимизируются.
- **Б1.** configure проходит на чистой системе: пакеты только из репозитория дистрибутива
  (mingw-w64, gcc, flex, bison), необязательные библиотеки выключены.
- **Б2.** `make __tooldeps__ dlls/<dll>/all` собирает PE-модуль и не тянет за собой сборку
  большей части дерева (посчитать собранные цели).
- **Б3.** Собранная DLL после снятия метки грузится системным Wine пользователя как native
  (`verify`).
- **Б4.** Исходники точной версии пользователя доступны (`apt source wine` или тег апстрима).

Что делать, если блокер найден:
- Б1 или Б2 — свой сборщик (см. выше).
- Б3 — разбираться в dllmgr, а не в сборке.
- Б4 — тег апстрима плюс сверка с патчами дистрибутива, которые касаются этой DLL.

**Результат проверки** (2026-11-06; песочница на Ubuntu 24.04 — той же базе, что у Mint 22;
тег `wine-11.0`; модули comctl32 и comctl32_v6):
- **Б1 — блокера нет.** Нужны только пакеты из репозитория: gcc, make, bison, flex,
  gcc-mingw-w64-i686, gcc-mingw-w64-x86-64.
  `configure --enable-archs=i386,x86_64 --without-x --without-freetype` — 19 с; предупреждения
  только про gettext, gnutls и звук.
- **Б2 — блокера нет**, свой сборщик не нужен.
  - `make -j4 __tooldeps__` — 9 с; `make -j4 dlls/comctl32/all dlls/comctl32_v6/all` — 39 с, для обеих архитектур.
  - Собрано 253 объектных файла: comctl32 — 56, comctl32_v6 — 70, winecrt0 — 30,
    ucrtbase — 16, uuid — 4, инструменты — 73.
  - Пересборка после правки одного файла — 4 с.
  - Место: исходники — 389 МБ, каталог сборки — 164 МБ.
- **Б3 — проверено частично.**
  - Собранные DLL несут метку builtin, её нужно снимать (Ф1).
  - Все обычные импорты i386-сборок (307 у comctl32, 384 у comctl32_v6) есть в экспортах
    Wine 9.0 из Ubuntu noble (пакет `libwine` 9.0~repack-4build3, i386).
  - Отложенные импорты (oleacc, winmm, uxtheme) статически не проверены: в сборке Wine
    каталог delay-import в PE пуст, где лежат дескрипторы — разобрать в И2 при написании
    `check`.
  - Загрузку в живом Wine 9 проверяет И0.
- **Б4 — для тега апстрима блокера нет:** shallow-клон `wine-11.0` с зеркала
  `wine-mirror/wine` — 8 с. `apt source wine` для точной версии пользователя не проверялся.

Итерации (после И1–И2 dllmgr):
- **С1 — диагност:** симптом, трассы, бисект по релизам на подготовленных вариантах, черновик отчёта; п. 7 (PR с улучшениями скилла) — с первого выпуска.
- **С2:** сборка одной DLL.
  - Первый шаг — проверка блокеров Б1–Б4; если есть Б1 или Б2 — свой сборщик.
  - Затем `wine-build-dll <dll> <tag|commit>` (кеш configure), шаблон репро и запуск под Xvfb.
  - Поиск тикетов через REST багзиллы.
- **С3:** цикл исправления, шаблон отчёта и проверка отчёта дешёвой моделью.
- **С4:** скилл пишет заплатки по §16 (после И6).
- **С5:** исправления в индексе как описания сборки (базовый тег + патч). CI индекса собирает
  их сам; бинарники, собранные ИИ, не принимаются.

## 16. Заплатки поверх незаменяемых DLL

DLL с unix-частью и ядро системы (ntdll, user32, gdi32, win32u…) заменить нельзя: их PE-часть
связана с unix-частью и wineserver внутренним протоколом конкретной версии Wine. Для них —
**заплатки**: маленькие DLL, которые загружаются в процесс программы и подменяют поведение
отдельных функций. Заплатки лежат в том же каталоге, что и варианты: тот же индекс, та же
модель правил (§3), тот же откат. Ни exe программы, ни Wine не меняются.

Как заплатка попадает в процесс:
1. **Стартовая DLL** — копия встроенной листовой DLL того же Wine, что у пользователя
   (например, `version.dll`), с одним добавленным импортом: `mwpatch.dll`. Код не меняется,
   поэтому совместимость гарантирована. Ставится обычным правилом: метка снята,
   `native,builtin` для этого exe. Добавить импорт в готовый PE — известный приём (так делает
   `setdll` из Microsoft Detours): новая секция с копией дескрипторов импорта и одним новым,
   переписанный указатель каталога импорта. Свой код на Go в `internal/pe`.
   - Какую DLL взять: первую заменяемую из статических импортов exe по списку предпочтений
     (`version`, `winmm`, `msimg32`…; список в конфиге). Подходящей нет — ошибка с просьбой
     выбрать вручную.
   - Стартовая DLL — производный вариант: она вычисляется из встроенной DLL целевого Wine.
     После обновления Wine reconcile пересоздаёт её сам, а не сообщает о расхождении.
2. **Загрузчик `mwpatch.dll`** (наш, маленький): в DllMain берёт имя exe процесса и грузит все
   DLL из `C:\windows\marwin\patches\<exe>\` в порядке имён. Конфигом служит сама раскладка
   каталога, парсер не нужен. Одна стартовая DLL на префикс обслуживает разные наборы
   заплаток для разных программ.
3. **Перехват** внутри заплатки: по умолчанию через IAT нужных модулей (exe и, если нужно,
   других DLL — например, вызовы comctl32 → user32); для модулей, загруженных позже, —
   `LdrRegisterDllNotification`. Если вызов надо поймать везде — inline-перехват готовой
   библиотекой (MinHook, BSD-2).
4. Для авторов — `mwpatch.h`: перехват через IAT и inline, уведомление о загрузке модулей,
   журнал в формате Wine (§17). Заплатки пишутся на C (mingw) или на Bp.

Манифест заплатки — как у варианта (§7), плюс:
```toml
kind    = "patch"
name    = "fsviewer-thumbstrip-scroll"
targets = ["user32!GetScrollInfo"]   # что перехватывает: для показа и поиска конфликтов
apps    = ["FSViewer.exe"]           # для каких программ сделана
```
`source` и `license` обязательны; CI индекса собирает заплатки из исходников сам и бинарники
не принимает. Две заплатки на одну функцию одной программы — предупреждение, порядок — по имени.

Гипотезы (проверяются в начале И6):
- **Г5.** Wine грузит стартовую DLL с добавленным импортом как обычную native (видно в `verify`).
- **Г6.** LoadLibrary из DllMain загрузчика под Wine не зависает (обычная практика загрузчиков
  плагинов). Если зависнет — запасной путь: заплатки прямо в импортах стартовой DLL; цена —
  по стартовой DLL на каждый набор заплаток.
- **Г7.** `LdrRegisterDllNotification` есть в Wine 9 (сверить по `dlls/ntdll`).

## 17. Сбор отладочной информации (`dllmgr diag`)

Агент (скилл wine-fix) или человек не должен каждый раз изобретать, как достать данные.
Одна команда собирает пакет фиксированной структуры с короткой выжимкой.

`dllmgr diag --app <exe-path> [--preset P …] [--compare <variant>] [--timeout N]`

Пакет `$WINEPREFIX/dllmgr/diag/<ts>-<exe>/`:
- `facts.json`:
  - версии Wine, дистрибутива и ядра; архитектура префикса;
  - действующие переопределения (переменная окружения, AppDefaults, глобальные);
  - правила dllmgr и их состояние;
  - exe: sha256, версия из ресурсов, разрядность, статические импорты;
  - загруженные модули (из `+loaddll`): native или builtin, хеш файла.
- `digest.txt` — выжимка не длиннее 60 строк:
  - загруженные управляемые DLL;
  - «No implementation»;
  - исключения (код, модуль + смещение);
  - первые `err:` и самые частые `fixme:`;
  - для relay — самые частые вызовы целевой DLL.
- `logs/*.log.zst` — полные логи, сжатые; размер ограничен (кольцевой буфер, лимит в конфиге).

Пресеты — данные (TOML в `presets/`), пополняются так же, как индекс:
- `load`: `+loaddll,warn+module` — что загрузилось и каких функций не хватило.
- `crash`: `+seh,+loaddll` и backtrace. Как получить backtrace без диалога (winedbg в
  автоматическом режиме через ключ AeDebug) — уточнить в И2.
- `relay:<dll>`: `+relay` только для этой DLL — значения `RelayInclude`/`RelayExclude` в
  `HKCU\Software\Wine\Debug`. Ставятся на время запуска и возвращаются через тот же слой реестра.
- `<dll>`: каналы конкретной DLL. Генерируются из исходников Wine нужного тега:
  `WINE_DEFAULT_DEBUG_CHANNEL` / `WINE_DECLARE_DEBUG_CHANNEL` в `dlls/<dll>/*.c`
  (`dllmgr presets gen`).
- Наши DLL и заплатки (cc580, §16) пишут журнал в формате Wine (`trace:<канал>:<функция> …`)
  и читают ту же переменную `WINEDEBUG`, поэтому их разбирает тот же код.

`--compare <variant>`: тот же сценарий запускается дважды — как есть и с временно
применённым вариантом (временный набор правил через reconcile, затем возврат); на выходе —
разница выжимок. Через это работает бисект DLL в скилле (§15).

Сценарий: интерактивный (пользователь работает в программе и закрывает её) или минимальный
репро из §15 п. 3; сценарии на xdotool — позже.
